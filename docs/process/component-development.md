# Component development

Use this process for each new public component or state. The repo-local [`ids-component-program` skill](../../.agents/skills/ids-component-program/SKILL.md) orchestrates the same workflow.

## 1. Select and brief

Take the next item from the [ordered catalog](../components/catalog.md), unless a documented consumer need justifies reprioritization. Add or update its component document with:

- confirmed use cases and the native HTML baseline;
- core, skin, and consumer ownership;
- proposed strict locals, states, relationships, and `ids-*` hooks;
- for skin work, the opt-in asset, no-skin control, skin-versus-brand ownership, smallest paired semantic colour surface, and CSS byte evidence;
- EN/RU keys only for universal text generated by IDS;
- explicit non-goals and deferred behavior;
- acceptance evidence required for `preview` and `stable`.

Planned options are not API. Do not implement multiple families in one change.

## 2. Preflight

For a new component or public state, Architecture and Accessibility review the brief before code. Add other roles only through the routing table in `AGENTS.md`:

- Simplicity for a new shared abstraction or dependency;
- Performance for assets, interaction, collections, or a measured performance claim;
- 37signals for architecture, dependency, or public philosophy claims;
- all five for the first skin/CSS, a renderer/dependency/build/frontend boundary, or stable release.

Reviewers define constraints and inspect evidence. The primary agent owns implementation and the final scoped decision.

### Team ownership

| Role | Owns |
| --- | --- |
| Primary agent | scope, implementation, conflict resolution, final evidence report |
| Rails Architecture and API | partial/API boundary, Engine integration, compatibility, packaging |
| Accessibility and Inclusive Design | semantics, names/relationships, keyboard/focus, AT and skin acceptance criteria |
| Simplicity and Dependency | unnecessary concepts/options, abstraction and dependency cost |
| Performance and Browser Platform | measured render/asset/interaction cost, native fallbacks, browser behavior |
| 37signals Philosophy and Evidence | Rails/browser-first architecture and accurate primary-source claims |

The detailed role contracts and exact routing table remain in `AGENTS.md`; this table does not make every role mandatory for every component.

## 3. Implement one vertical slice

Use a namespaced strict-local partial and Rails/browser primitives. Finish the component's semantic contract, gallery state, documentation, and proportional tests together. A skin may follow in the same family, but core semantics must work without it.

Do not add a public base component, polymorphic renderer, slots DSL, shared test DSL, CSS/JavaScript, token, skin, or dependency just to anticipate later catalog entries. For skin work, follow [ADR 0008](../architecture/0008-optional-default-skin.md): one opt-in default asset, no automatic loading, and only colour pairs consumed by the current slice.

## 4. Verify

Use [component testing](../quality/component-testing.md) to select the smallest sufficient evidence. During implementation, run the changed test file. Before handoff, run the default fast task. Package, compatibility, browser, and stable-release checks stay at their documented risk level.

Owned strings use `imagusu_design_system.*`. English is canonical and Russian ships in parity. Product wording remains a required component local and belongs to the host application.

## 5. Review and record

Run only routed diff reviewers, resolve blockers, and rerun affected checks. In the same change:

- update the catalog marks and status;
- link the component contract and evidence;
- record manual checks actually performed;
- keep planned and unprovable evidence visibly separate.

An agent verdict cannot replace a test or move a component to `stable`. Stable status requires every item promised by its brief and the stable evidence in `AGENTS.md`.
